# Requirement details template entry

Use the [canonical requirement summary template](.github/skills/x-ipe-task-based-requirement-gathering/references/requirement-details-template.md)
when creating/appending requirement-details. This existing resource path remains
available for consumers; it delegates to one domain form instead of a conflicting
second version without Epic/acceptance/impact fields.

Retain Project Overview, User Request, Clarifications, High-Level Requirements,
Constraints, Open Questions and Linked Mockups, plus the canonical Epic, acceptance,
scope, risk, Related Features, impact and revision evidence fields. Use a concise
combined section for bounded work, not a separate mandatory analysis document.
Include its Outcome / Goal Frame and Requirement Mapping: stable IDs tie intent,
stakeholder outcome, planned success evidence and constraints to requirements.
Qualitative scenarios are valid; delivery is not an observed stakeholder outcome.
Keep requested language and project-root-relative links; never place an EPIC ID
in a Feature ID field. Stable identifiers and task_completion_output are unchanged.
